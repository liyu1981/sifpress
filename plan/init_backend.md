# init_backend.md — Backend Plan (SQLite + RBAC + Markdown Pages)

Scope: the server side of the single-file PHP app. Multi-user, RBAC, SQLite
(FTS5, WAL), versioned schema migrations, and markdown pages as the core
entity.

## Key decisions

1. **Migrations travel inside the artifact.** The whole point of this project
   is that `dist/index.php` is a single, copy-anywhere file. SQL migration
   scripts therefore live in `migrations/*.sql` as the *authoring* source of
   truth, and `build.php` embeds them into the artifact at build time (same
   mechanism as the inlined React HTML). `dist/index.php` stays one file; the
   `migrations/` folder is never needed at runtime.
2. **Schema version is tracked in the DB; bootstrap only *detects*.** A
   `_migrations` table records applied versions. Every request bootstrap opens
   the DB, sets pragmas, and compares applied vs. embedded versions. If they
   differ, the app enters **migration-needed mode**: the SPA is served with a
   maintenance hint and the JSON API (except `system.status`) returns
   `503 migration_required`. Migrations are applied **on demand** through a
   dedicated `?module=migration` endpoint (GET = status, POST = run). Nothing
   is applied automatically.
3. **Sessions are DB-backed**, not PHP `$_SESSION` files. A random token in an
   `HttpOnly; SameSite=Lax` cookie maps to a `sessions` row (token stored
   hashed). No PHP session config needed, works anywhere the single file
   works.
4. **RBAC = roles + permissions, many-to-many.** Users have roles, roles have
   permissions. Permissions are string codes (`pages.read`, `pages.write`,
   `pages.delete`, `users.manage`, `roles.manage`). `admin` / `editor` /
   `viewer` default roles are seeded idempotently during migration.
5. **Page editing is ownership-aware.** Role `pages.write` is necessary but
   not sufficient: a user may edit a page only if they are the **author** or
   were **granted edit access** to that page (by its author or an admin).
   Admins bypass the grant check. Grants live in a `page_grants` table.
6. **FTS5 uses the `trigram` tokenizer.** `unicode61` cannot segment CJK text
   (each Chinese run becomes one token), and the app is en/zh. `trigram`
   handles CJK substring search natively. FTS is an external-content table
   with sync triggers on `pages` (no content duplicated).
7. **DB location: `<folder>/sys.db`.** Folder precedence: `APP_DB_DIR`
   env (dev sets `./var/single-php`), else `<DOCUMENT_ROOT>/../single-php`
   (production default — the `single-php` folder sits beside the web root),
   else `<artifact dir>/var/single-php` for CLI. WAL mode (`-wal`/`-shm`
   files live beside it).
8. **First admin uses default credentials with forced change.** First
   migration seeds a default account (username `admin`, password `admin123`,
   overridable via `ADMIN_PASSWORD` env) flagged `must_change_password`. The
   app blocks normal use until the password is changed.

src/

Fragment assembly order (build.php `$parts`): `bootstrap.php`, `db.php`,
`migration.php`, `auth.php`, `api.php`, `spa.php`, `embed.php`,
`migrations.php`, `router.php`. PHP `const` order only matters before first use
at runtime, and all fragments are defined before `router.php` dispatches, so
placement is safe.

## Routing model

```
?module=api        -> JSON API (?action=...)
?module=migration  -> migration status / run (?action=status|run)
?u=...             -> client-side SPA route (anything else)
```

## 01 — Database (SQLite + FTS5, WAL)

### Configuration

`db.php` owns a single `PDO` instance per request (static cache). Open and
configure once:

```php
function db(): PDO
{
    static $pdo = null;

    if ($pdo === null) {
        $pdo = new PDO('sqlite:' . db_path());
        $pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
        $pdo->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE, PDO::FETCH_ASSOC);
        $pdo->exec('PRAGMA journal_mode = WAL');
        $pdo->exec('PRAGMA synchronous = NORMAL');
        $pdo->exec('PRAGMA foreign_keys = ON');
        $pdo->exec('PRAGMA busy_timeout = 5000');
        $pdo->exec('CREATE TABLE IF NOT EXISTS _migrations (
            version    TEXT PRIMARY KEY,
            applied_at TEXT NOT NULL DEFAULT (datetime(\'now\'))
        )');
    }

    return $pdo;
}

function db_path(): string
{
    $dir = db_dir();

    if (!is_dir($dir)) {
        mkdir($dir, 0777, true);
    }

    return $dir . '/sys.db';
}

function db_dir(): string
{
    $env = getenv('APP_DB_DIR');

    if ($env !== false && $env !== '') {
        return rtrim($env, '/\\');          // dev: ./var/single-php
    }

    $webRoot = (string) ($_SERVER['DOCUMENT_ROOT'] ?? '');

    if ($webRoot !== '') {
        return rtrim($webRoot, '/\\') . '/../single-php';  // production default
    }

    return dirname(__FILE__) . '/var/single-php';          // CLI fallback
}
```

Notes:

- No migrations run here. Opening the DB creates the (empty) file and the
  `_migrations` bookkeeping table only — idempotent and safe on every request.
- The database folder must be writable by the server process and is created
  on demand. In production the default is `<DOCUMENT_ROOT>/../single-php`
  (the `single-php` folder beside the web root); override the folder with
  `APP_DB_DIR`. Dev sets `APP_DB_DIR=./var/single-php` (gitignored).

### Version detection

```php
function db_version(): array     // ['applied' => [...], 'latest' => [...]]

function db_needs_migration(): bool
{
    $v = db_version();

    return $v['applied'] !== $v['latest'];   // ordered lists compared
}
```

- `applied` = `SELECT version FROM _migrations`.
- `latest` = `array_keys(MIGRATIONS)`.
- A fresh DB has an empty `applied` list → needs migration.
- Used by `spa.php` (maintenance meta tag), `api.php` (503 gating), and
  `migration.php`.

### Migration engine

**Source of truth:** `migrations/NNNN_name.sql`, numbered and ordered.

**Runtime:** `build.php` reads the folder and injects the contents into the
`migrations.php` fragment as a PHP array constant (same embedding technique as
the HTML):

```php
// in src/migrations.php, regenerated by build.php
const MIGRATIONS = [
    '0001_initial_schema.sql' => '... full SQL ...',
    '0002_pages_fts.sql'      => '... full SQL ...',
];
```

`build.php` asserts every `*.sql` in `migrations/` is present in `MIGRATIONS`
(and vice-versa) so nothing can drift.

**Runner** — called *only* from the `?module=migration&action=run` endpoint:

```php
function db_migrate(PDO $pdo): array
{
    $applied = $pdo->query('SELECT version FROM _migrations')
        ->fetchAll(PDO::FETCH_COLUMN);

    $done = [];
    foreach (array_keys(MIGRATIONS) as $version) {
        if (in_array($version, $applied, true)) {
            continue;
        }

        $pdo->exec('BEGIN IMMEDIATE'); // write lock up front — safe under concurrency
        try {
            $pdo->exec(MIGRATIONS[$version]);
            $stmt = $pdo->prepare('INSERT INTO _migrations (version) VALUES (?)');
            $stmt->execute([$version]);
            $pdo->exec('COMMIT');
            $done[] = $version;
        } catch (Throwable $e) {
            $pdo->exec('ROLLBACK');
            throw $e;
        }
    }

    return $done;
}
```

Rules:

- Migrations run in filename order (zero-padded numbers).
- Each migration is one transaction; partial migrations roll back.
- Never edit an applied migration — add a new one.
- `_migrations` is the canonical "DB version".
- On a successful `run`, seeds run afterward (RBAC roles + default admin —
  see `02`).

### Migration endpoint (`?module=migration`)

Handled in `src/migration.php`:

| URL | method | response |
| --- | ------ | -------- |
| `?module=migration` or `?action=status` | GET | `{migrate_required, version, latest, migrations: [{version, applied}]}` |
| `?module=migration&action=run` | POST | applies pending migrations + seeds; returns `{applied: [...], latest, migrate_required:false}` |

- Public and unauthenticated by design: a fresh install has no users yet, and
  the runner is forward-only/idempotent (already-applied versions are skipped).
  It errors if called with nothing pending (`409 already up to date`) to avoid
  casual poking.
- Concurrency: `BEGIN IMMEDIATE` + `busy_timeout` prevent two concurrent runs
  from racing.

### Migration-needed mode (maintenance)

- **SPA:** `serve_spa()` calls `db_needs_migration()` and injects
  `<meta name="app-maintenance" content="1">`. The frontend reads it and shows
  a "database needs migration" screen with a button that POSTs to
  `?module=migration&action=run`.
- **API:** every action except `system.status` returns
  `503 {error: 'migration_required', version, latest}`. `system.status`
  returns the same info for the setup/maintenance screen.

### Schema — `0001_initial_schema.sql`

```sql
CREATE TABLE users (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    username            TEXT    NOT NULL UNIQUE,
    email               TEXT    UNIQUE,              -- optional
    name                TEXT    NOT NULL DEFAULT '',
    password_hash       TEXT    NOT NULL,
    must_change_password INTEGER NOT NULL DEFAULT 0,
    is_active           INTEGER NOT NULL DEFAULT 1,
    created_at          TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at          TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE roles (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    code        TEXT NOT NULL UNIQUE,  -- 'admin' | 'editor' | 'viewer'
    name        TEXT NOT NULL,         -- display name (i18n-friendly)
    description TEXT NOT NULL DEFAULT ''
);

CREATE TABLE permissions (
    id   INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL UNIQUE          -- 'pages.read', 'pages.write', ...
);

CREATE TABLE role_permissions (
    role_id       INTEGER NOT NULL REFERENCES roles(id)       ON DELETE CASCADE,
    permission_id INTEGER NOT NULL REFERENCES permissions(id) ON DELETE CASCADE,
    PRIMARY KEY (role_id, permission_id)
);

CREATE TABLE user_roles (
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, role_id)
);

CREATE TABLE sessions (
    token_hash TEXT    PRIMARY KEY,     -- hex sha256 of the raw cookie token
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at TEXT    NOT NULL DEFAULT (datetime('now')),
    expires_at TEXT    NOT NULL,
    ip         TEXT    NOT NULL DEFAULT '',
    user_agent TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX idx_sessions_user   ON sessions(user_id);
CREATE INDEX idx_sessions_expiry ON sessions(expires_at);

CREATE TABLE pages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    slug       TEXT    NOT NULL UNIQUE,
    title      TEXT    NOT NULL DEFAULT '',
    content_md TEXT    NOT NULL DEFAULT '',
    status     TEXT    NOT NULL DEFAULT 'draft',  -- 'draft' | 'published'
    created_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    updated_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    created_at TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT    NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_pages_updated ON pages(updated_at DESC);

CREATE TABLE page_grants (
    page_id    INTEGER NOT NULL REFERENCES pages(id) ON DELETE CASCADE,
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    granted_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    created_at TEXT    NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (page_id, user_id)
);
```

### Schema — `0002_pages_fts.sql`

External-content FTS table (no duplicated body text) with sync triggers:

```sql
CREATE VIRTUAL TABLE pages_fts USING fts5(
    title,
    content_md,
    content = 'pages',
    content_rowid = 'id',
    tokenize = 'trigram'
);

CREATE TRIGGER pages_ai AFTER INSERT ON pages BEGIN
    INSERT INTO pages_fts(rowid, title, content_md)
    VALUES (new.id, new.title, new.content_md);
END;

CREATE TRIGGER pages_ad AFTER DELETE ON pages BEGIN
    INSERT INTO pages_fts(pages_fts, rowid, title, content_md)
    VALUES ('delete', old.id, old.title, old.content_md);
END;

CREATE TRIGGER pages_au AFTER UPDATE ON pages BEGIN
    INSERT INTO pages_fts(pages_fts, rowid, title, content_md)
    VALUES ('delete', old.id, old.title, old.content_md);
    INSERT INTO pages_fts(rowid, title, content_md)
    VALUES (new.id, new.title, new.content_md);
END;
```

**Tokenizer decision: `trigram` over `unicode61`**

- `unicode61` treats a contiguous run of CJK characters as a *single* token,
  so Chinese text is effectively unsearchable. The app is en/zh.
- `trigram` indexes all 3-char substrings → substring search works for both
  English and CJK with no external segmentation library.
- Cost: queries shorter than 3 chars return nothing; every 3-char substring
  is stored (larger index). Acceptable for page content.

**Search query**

```sql
SELECT p.id, p.slug, p.title,
       snippet(pages_fts, 1, '<mark>', '</mark>', '…', 12) AS excerpt
FROM pages_fts
JOIN pages p ON p.id = pages_fts.rowid
WHERE pages_fts MATCH :match      -- e.g. '"foo bar"*' via build_match()
  AND p.status = 'published'      -- caller decides
ORDER BY rank
LIMIT :limit;
```

Queries are never spliced raw into MATCH. A small `build_match(string $q)`
helper escapes user input into a safe FTS5 string (`"..."*` quoted-phrase with
prefix wildcard, falling back to nothing when < 3 chars). Plan future work:
two-column ranking (title match boosted over body) if relevance matters.

## 02 — Authentication & RBAC

### Sessions (DB-backed)

No PHP `$_SESSION` files — everything is in SQLite, so the single-file
artifact works with zero PHP configuration.

**Flow**

1. Login verifies credentials, then creates a session:
   - `$token = bin2hex(random_bytes(32))` → returned to the client **only
     once** as the cookie value.
   - Store `token_hash = hash('sha256', $token)` + `user_id` + `expires_at`
     (30 days) + `ip` + `user_agent` in `sessions`.
   - `setcookie('session', $token, ['httponly' => true, 'samesite' => 'Lax',
     'secure' => true, 'path' => '/'])`.
2. Every request reads the cookie, hashes it, looks up a matching
   non-expired row, and loads the user.

```php
function current_user(): ?array
{
    static $user = false;

    if ($user === false) {
        $token = $_COOKIE['session'] ?? null;
        $user = $token === null ? null : lookup_session($token);
    }

    return $user;
}
```

Why store only a hash: a `SELECT` from SQLite plus a leaked-cookie list (the
DB file) can't be used to mint sessions.

**Expiry/cleanup:** sessions are expired by `expires_at < now` on lookup;
a `DELETE FROM sessions WHERE expires_at < now` sweep runs opportunistically
(a few rows) on login. Logout deletes the row and clears the cookie.

### Password hashing

- `password_hash($password, PASSWORD_DEFAULT)` (bcrypt) on create/update.
- `password_verify()` on login.
- Never store or log raw passwords; never return `password_hash` in API
  responses.
- Login failure is deliberately identical for "no such user" and "wrong
  password" (`401 Unauthorized`).

### First admin (default credentials + forced change)

- First migration run: when the `users` table is empty, create the default
  admin:
  - `username = 'admin'`
  - `password = getenv('ADMIN_PASSWORD') ?: 'admin123'`
  - `must_change_password = 1`
- The default credentials are documented (and overridable) but **never
  usable beyond setup**: see `auth.changePassword` in `03` — while
  `must_change_password` is set, the only API actions allowed are
  `auth.changePassword`, `auth.logout`, and `auth.me`. The frontend forces the
  change flow before showing any app UI.
- After a successful change, `must_change_password` is cleared.

### RBAC model

Three tables in `0001_initial_schema.sql`:

```
users ──< user_roles >── roles ──< role_permissions >── permissions
```

- **permissions**: string codes, e.g. `pages.read`, `pages.write`,
  `pages.delete`, `users.manage`, `roles.manage`.
- **roles**: named bundles of permissions; users carry roles.
- Checking is "user has ≥1 role that grants the permission".

**Seeding** (idempotent, runs at the end of a successful migration run):
`seed_rbac(PDO $pdo)` upserts by unique code — no-ops once present:

| role    | permissions                                              |
| ------- | -------------------------------------------------------- |
| `admin` | all of the above (and any future ones)                   |
| `editor`| `pages.read`, `pages.write`, `pages.delete`              |
| `viewer`| `pages.read`                                             |

Admin gets every permission in the `permissions` table via a
`WHERE permission_id IN (SELECT id FROM permissions)` insert, so it stays
"all-powerful" as new permissions are added.

**Helpers (`auth.php`)**

```php
function require_auth(): array;                  // 401 if not logged in
function require_permission(string $perm): void; // 401 / 403 wrapper
function is_admin(array $user): bool;
function can(PDO $pdo, int $userId, string $permission): bool; // static-cached
function can_edit_page(PDO $pdo, array $user, int $pageId): bool;
function require_page_edit(array $page): void;   // 403 unless allowed
```

Implementation sketch for `can()` — one join, cached per request:

```sql
SELECT COUNT(*)
FROM user_roles ur
JOIN role_permissions rp ON rp.role_id = ur.role_id
JOIN permissions p        ON p.id = rp.permission_id
JOIN users u              ON u.id = ur.user_id
WHERE u.id = :uid
  AND u.is_active = 1
  AND p.code = :perm
```

`require_permission()` maps results to HTTP: `401` when not authenticated,
`403` when authenticated but lacking the permission. `can()` never raises.

### Page editing (ownership + grants)

Role permission is necessary but not sufficient:

```
can_edit_page(user, page) =
    is_admin(user)
    OR ( user has 'pages.write'
         AND ( page.created_by == user.id
               OR EXISTS(SELECT 1 FROM page_grants
                         WHERE page_id = page.id AND user_id = user.id) ) )
```

Rules:

- **Author** edits their own pages without any grant.
- **Admin** edits anything.
- **Others** edit only pages where the author **or an admin** has explicitly
  granted them access (`page_grants` row). Granting requires `pages.write`
  capability *and* being the page author or admin.
- Grants are revoked by the author or an admin.
- A grant to a user without the `pages.write` role is rejected (pointless).
- Read is role-based (`pages.read`); delete stays role-based
  (`pages.delete`).

### Guard rails

- Every state-changing action checks `require_auth()` **and** the relevant
  `require_permission()` (plus `require_page_edit()` where applicable).
- `users.manage` / `roles.manage` actions only for admins.
- Users marked `is_active = 0` are rejected at lookup — immediate, global
  revoke without touching sessions.
- CSRF: JSON API + `SameSite=Lax` cookie covers same-site requests; state-
  changing calls additionally must not be form-encodable — see 03 below.

## 03 — API surface

Keeps the existing protocol: `?module=api&action=...`. The `handle_api`
switch in `api.php` gains auth/RBAC guards at the top and new actions below.

### Conventions

- **Action names** are dotted (`auth.login`, `pages.list`) — dots are safe in
  query params and read cleanly.
- **Methods:** GET = read, POST = create, PATCH = partial update,
  DELETE = delete.
- **Body:** JSON, via the existing `read_json_body()`.
- **Responses:** existing `json_response()` shape — data object on success,
  `{ "error": "..." }` on failure.
- **Errors:**
  | code | meaning |
  | ---- | ------- |
  | 400 | bad request / invalid body |
  | 401 | not authenticated (or bad credentials) |
  | 403 | authenticated but lacking permission / grant |
  | 404 | unknown action / resource |
  | 409 | unique conflict (slug/username taken, no-op migration) |
  | 422 | validation failed (field-level details in `errors`) |
  | 503 | migration required |
  | 405 | wrong method for action |

### Migration gating

Top of `handle_api()`:

```php
if (db_needs_migration() && $action !== 'system.status') {
    json_response(['error' => 'migration_required',
                   'version' => ..., 'latest' => ...], 503);
}
```

### Auth actions

| action | method | auth | description |
| ------ | ------ | ---- | ----------- |
| `auth.login` | POST | – | `{username, password}` → 200 + sets `session` cookie; returns user+roles+`must_change_password` |
| `auth.logout` | POST | yes | deletes session, clears cookie |
| `auth.me` | GET | optional | current user + roles + granted permission codes + `must_change_password` (`null` if anonymous) |
| `auth.changePassword` | POST | yes | `{current_password?, new_password}`; clears `must_change_password` (see below) |
| `system.status` | GET | – | app name, schema `version` + `latest`, `migrate_required`, setup state |

`auth.changePassword`: when `must_change_password` is set, `current_password`
is not required and this is the *only* action besides `auth.me`/`auth.logout`
the user may call — enforced in `handle_api`. Password is validated (min 8
chars, contains a letter and a digit) with 422 details.

### Pages actions

Guards: `pages.read` to read/list/search; `pages.write` + ownership/grant for
write; `pages.delete` for delete.

| action | method | body/params | description |
| ------ | ------ | ----------- | ----------- |
| `pages.list` | GET | `?status=&page=&per_page=&q=` | paginated list, `updated_at` desc; `q` routes to search |
| `pages.get` | GET | `slug` or `id` (param) | full page incl. `content_md`, author names, `can_edit` for current user |
| `pages.create` | POST | `{slug, title, content_md, status}` | validates slug uniqueness, `status` in `draft\|published`; author = current user |
| `pages.update` | PATCH | `{id, ...fields}` | `require_page_edit()`; sets `updated_by`, bumps `updated_at` |
| `pages.delete` | DELETE | `id` | hard delete (FTS cleaned via trigger); `pages.delete` |
| `pages.search` | GET | `?q=&status=` | FTS5 search, returns ranked results + excerpt |
| `pages.grants` | GET | `?page_id=` | list grantee usernames for a page (author/admin only) |
| `pages.grant` | POST | `{page_id, username}` | add edit grant (author/admin; target must have `pages.write`) |
| `pages.revokeGrant` | POST | `{page_id, username}` | remove edit grant (author/admin) |

`pages.get` returns `can_edit: bool` so the UI only shows the edit affordance
when actually permitted (writer without grant sees read-only).

Validation (422 with `errors` map):
- `slug`: `^[a-z0-9]+(?:-[a-z0-9]+)*$`, 1–64 chars, unique.
- `title`: 1–200 chars.
- `content_md`: size-capped (e.g. 1 MB) to protect the DB.
- `status`: one of `draft` / `published`.

### Users & roles actions (admin)

| action | method | permission | description |
| ------ | ------ | ---------- | ----------- |
| `users.list` | GET | `users.manage` | list users + roles, not password hashes |
| `users.create` | POST | `users.manage` | `{username, email?, name, password, role_ids}` |
| `users.update` | PATCH | `users.manage` | name / email / password / `is_active`; username immutable |
| `users.setRoles` | POST | `roles.manage` | replace a user's role set |
| `roles.list` | GET | `roles.manage` | roles + their permissions |

### Auth guard placement

Top of `handle_api()`:

```php
$public = ['index', 'auth.login', 'auth.me', 'system.status'];

if (!in_array($action, $public, true)) {
    require_auth();          // 401
}

if (($user = current_user()) !== null && $user['must_change_password']
        && !in_array($action, ['auth.changePassword', 'auth.logout', 'auth.me'], true)) {
    json_response(['error' => 'password_change_required'], 403);
}

// per-action permission gates inside each case:
//   case 'pages.delete': require_permission('pages.delete'); ...
```

### CSRF

- Cookie is `SameSite=Lax` (strong default; state-changing cross-site POSTs
  are blocked by the browser).
- State-changing actions additionally reject request bodies whose
  `Content-Type` is not `application/json` (HTML forms can't trigger them).
- If the app ever needs to accept cross-origin clients, revisit with a token
  header.

### Not in scope (v1)

- Page history/versioning (a `page_versions` table + diff is a clean follow-up
  since `pages.update` already records `updated_by`).
- Soft delete, rate limiting (add an API-key or token-bucket layer later; auth
  login at minimum can add a per-IP delay).

## 04 — Build & deployment

### `build.php` changes

1. **New fragments** added to `$parts` (order: `bootstrap.php`, `db.php`,
   `migration.php`, `auth.php`, `api.php`, `spa.php`, `embed.php`,
   `migrations.php`, `router.php`).
2. **Embedded migrations.** The `migrations.php` fragment holds a region with
   markers, exactly like `embed.php`:

   ```
   // ___BEGIN_MIGRATIONS___
   const MIGRATIONS = [];
   // ___END_MIGRATIONS___
   ```

   `build.php` reads `migrations/*.sql`, sorts by filename, and regenerates the
   region via `var_export` (same technique as the HTML embed):

   ```php
   const MIGRATIONS = [
       '0001_initial_schema.sql' => '...',
       '0002_pages_fts.sql'      => '...',
   ];
   ```

   It also verifies a 1:1 match between the `migrations/` folder and
   `MIGRATIONS` keys so drift fails the build loudly.

3. **No other behavior changes** — SPA serving, meta injection, inlining all
   stay untouched.

### Runtime request flow

```
router.php
  ├─ module=migration -> handle_migration()   // status / run (applies + seeds)
  ├─ module=api       -> handle_api()
  │                     ├─ db()               // open + pragmas + version check
  │                     ├─ if migration needed: 503 (except system.status)
  │                     ├─ auth guards + per-action permissions
  └─ else             -> serve_spa()          // injects app-maintenance meta if needed
```

`db()` is lazy and static-cached; when up to date, bootstrap cost is one
`SELECT` from `_migrations` + one `SELECT` per `can()` (also cached).

### Deployment notes

- Ship `dist/index.php` plus a writable database folder (default:
  `<DOCUMENT_ROOT>/../single-php`, overridable with `APP_DB_DIR`). The DB,
  `-wal`, and `-shm` files appear there on first request; the first request
  (or a visit to `?module=migration&action=run`) creates the schema and
  seeds the default admin.
- No PHP extension beyond `pdo_sqlite`/`sqlite3` is needed; both ship with
  stock PHP. FTS5 + trigram require SQLite ≥ 3.34 (env has 3.45.1).
- Backups: with WAL, copy `sys.db` + `sys.db-wal` together (or run
  `PRAGMA wal_checkpoint(TRUNCATE)` first). `sqlite3 <folder>/sys.db
  ".backup out.db"` is the safe one-shot option.
- The single artifact remains fully portable — no rewrites, no PHP session
  config, no config file.

### Verification plan

1. Fresh DB: GET `?module=migration` shows `migrate_required:true`; any API
   action except `system.status` → 503; SPA HTML contains the maintenance
   meta tag.
2. POST `?module=migration&action=run` → schema applied, RBAC seeded, default
   admin created; GET again shows `migrate_required:false`; a second run →
   409.
3. Old DB: delete the `_migrations` row for `0002`, request again → migration-
   needed mode; run endpoint re-applies `0002` in a transaction.
4. Concurrent runs against a fresh DB → `BEGIN IMMEDIATE` + `busy_timeout`
   prevent races.
5. First login as `admin`/`admin123` → blocked from everything except
   password change; after change, full access. curl smoke tests (login → me →
   create page → list → search → grant editor → editor edits → delete).
6. `php build.php` after adding/removing a `migrations/*.sql` file either
   embeds it or fails the build.

## 05 — Frontend integration (brief)

Backend-first plan; these are the hooks the React side will need when it
lands. Exact UI work is a separate task.

### Migration / setup screen

- On boot, read `<meta name="app-maintenance">` (or `system.status`); if
  `migrate_required`, render a full-screen "database needs migration" view
  with a button that POSTs `?module=migration&action=run`, then reloads.
- If `setup needed` (no users) and no maintenance flag, show setup info with
  the default admin credentials reminder.

### API client (`frontend/src/lib/api.ts`)

- `api()` already hits `?module=api&action=...` relative to the document —
  unchanged.
- Add a helper to send JSON for POST/PATCH/DELETE (cookies are sent
  same-origin by default).
- Error mapping: parse `{error, errors}` and surface 401/403/503 distinctly.

### Auth context

- `AuthProvider` + `useAuth()`: on mount calls `auth.me`; holds
  `{ user, roles, permissions, must_change_password }`; exposes `login()`,
  `logout()`, `changePassword()`.
- Permission helper: `usePermission('pages.write')` or `has('pages.write')`
  using the permission codes from `auth.me`.
- When `must_change_password` is true, render the forced password-change
  screen and block all other navigation.

### Route guards

- `/login` page: username + password, calls `auth.login`, redirects.
- Home/article routes: article detail calls `pages.get` and shows the Edit
  button only when `can_edit` is true (backend also enforces).
- `/editor/:slug` — new route using the existing markdown editor components
  (`frontend/src/components/markdown/`, `frontend/src/lib/markdown/`), wired to
  `pages.get` / `pages.create` / `pages.update`; grant management UI for
  authors/admins.
- `/settings` — account settings (name, password) for normal users and, for
  admins, the user management screen (`users.*`, `roles.*`).
- Unauthenticated access to guarded routes → redirect to `/login` with a
  `?next=` return path.
